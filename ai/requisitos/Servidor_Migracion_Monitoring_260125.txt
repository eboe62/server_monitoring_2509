2.6 Justificación del uso de wrappers mínimos (IaC)
----------------------------------
✔ 2.6.1 Contexto
En este proyecto, el directorio `scripts/` se considera infraestructura operativa
(IaC) y no parte del código fuente Python distribuible.

La lógica ejecutable vive exclusivamente bajo `src/`, organizada como paquetes
Python importables y ejecutables mediante `python3 -m`.

Los scripts en `scripts/` actúan como wrappers mínimos.

✔ 2.6.2 Objetivo de los wrappers
El uso de wrappers mínimos persigue los siguientes objetivos:

- Garantizar portabilidad total del sistema entre servidores
- Evitar dependencias implícitas del sistema operativo
- Eliminar acoplamientos a rutas absolutas del host
- Permitir ejecución consistente en:
  - Host Linux
  - Contenedores Docker
  - Entornos efímeros o de recuperación
- Mantener la infraestructura 100% reproducible (IaC)

✔ 2.6.3 Principio arquitectónico
La infraestructura no ejecuta archivos Python directamente.
La infraestructura ejecuta módulos Python.

Esto implica:
- Nunca invocar: /ruta/al/archivo.py
- Ejecutar siempre: python3 -m paquete.modulo

Los wrappers:
- No contienen lógica de negocio
- No importan código Python
- No duplican configuración
- Únicamente:
  - Preparan el entorno mínimo
  - Invocan el módulo correcto

✔ 2.6.4 Esquema conceptual
ANTES (modelo acoplado al host):

cron / shell
  |
  v
/usr/bin/python3 /opt/monitoring/log_ingestor/log_ingest_batch.py
  |
  +-- depende de rutas
  +-- depende del host
  +-- frágil ante refactors

DESPUÉS (modelo IaC autónomo):

cron / shell (wrapper)
  |
  v
python3 -m log_ingestor.log_ingest_batch
  |
  v
src/log_ingestor/log_ingest_batch.py
  |
  +-- ejecutable como módulo
  +-- independiente de rutas físicas
  +-- portable y reproducible

✔ 2.6.5 Decisión consciente
Esta arquitectura es intencionada.

No se busca:
- Convertir `scripts/` en paquete Python
- Ejecutar lógica directamente desde cron
- Acoplar la infraestructura al layout interno de src/

Se busca:
- Separación estricta entre infraestructura y lógica
- Capacidad de refactorizar src/ sin romper cron ni scripts
- Infraestructura desplegable en cualquier servidor sin ajustes manuales

Esta decisión se alinea con:
- Infraestructura como Código (IaC)
- Principios de portabilidad y reproducibilidad
- Ejecución determinista y auditable

2.7 Ejecución de cronjobs en contenedores
----------------------------------
ANTES
Los cronjobs ejecutaban scripts shell que, a su vez, invocaban
archivos Python de forma directa mediante rutas absolutas
(por ejemplo /opt/monitoring/.../*.py). Este modelo
acoplaba la ejecución al layout del filesystem del host, al PYTHONPATH y al
entorno concreto donde se desplegaba el servidor.

La relación entre cronjobs, scripts y lógica Python no estaba
formalizada, y la activación de cron podía fallar silenciosamente
si el entorno no cumplía ciertas condiciones (Docker, secrets,
servicios externos, permisos de filesystem).

No existía una enumeración explícita de precondiciones necesarias
para ejecutar cronjobs dentro de contenedores.

DESPUÉS
Todos los cronjobs están modelados como wrappers mínimos bajo
scripts/, por lo tanto toda ejecución Python se realiza exclusivamente invocando módulos Python
mediante:

    python3 -m <paquete>.<módulo>

La invocación se realiza a través de wrappers mínimos en scripts/, cuya única
responsabilidad es:
- preparar el entorno de ejecución
- ejecutar el módulo Python correspondiente
- no contener lógica de negocio

El código ejecutable reside únicamente en src/, tratado como paquete Python.
Este enfoque garantiza:
- coherencia de imports
- portabilidad entre entornos
- ejecución reproducible en contenedores
- independencia del layout del filesystem del host

La relación cronjob → módulo Python queda explícita y es la siguiente:

- alert_risk.sh
  → python3 -m log_ingestor.alert_risk

- log_ingest_batch.sh
  → python3 -m log_ingestor.log_ingest_batch

- log_kern_batch.sh
  → python3 -m log_ingestor.log_kern_batch

- log_fail2ban_batch.sh
  → python3 -m log_ingestor.log_fail2ban_batch

- log_ip_geolocation.sh
  → python3 -m log_ingestor.log_ip_geolocation

- log_honeypot_geolocation.sh
  → python3 -m log_ingestor.log_honeypot_geolocation

- docker_resources.sh
  → python3 -m resource_monitor.docker_resources

Los scripts de backup (backup_postgres.sh, backup_restore.sh)
se consideran scripts operativos de infraestructura y dependen
explícitamente de Docker y PostgreSQL; no se tratan como cronjobs
Python puros.

✔ 2.7.1 Precondiciones explícitas
La activación de cronjobs en contenedores queda condicionada a que
el entorno cumpla explícitamente las siguientes precondiciones:

- Docker CLI disponible y permisos para ejecutar docker exec / cp
- Existencia de un contenedor Python con el código bajo src/
- Dependencias Python instaladas (psycopg2, requests, etc.)
- PostgreSQL accesible y credenciales válidas
- SMTP / relay accesible para notificaciones
- Sistema de ficheros preparado:
  - /var/log con permisos de escritura
  - /opt/monitoring/backups existente
  - /opt/monitoring/smtp_relay/.env presente
  - /opt/monitoring/smtp_relay/secrets/* presentes y protegidos

Si alguna de estas precondiciones no se cumple, los cronjobs pueden
fallar por errores de import-time, lectura de secrets, permisos,
conectividad o dependencias externas.

Estos riesgos se consideran conocidos y aceptados en esta fase.
No se aplican correcciones automáticas ni workarounds.

2.8 Desacoplamiento de configuración y dependencias
----------------------------------
ANTES
El módulo monitoring/common/config.py cargaba variables de entorno (.env) y
leía secrets del filesystem en tiempo de importación. Esto introducía
dependencias rígidas a rutas absolutas (/opt/monitoring/...) y provocaba
fallos inmediatos al importar el módulo si dichos recursos no existían.

Este comportamiento impedía importar el código en entornos limpios y hacía
frágil cualquier validación previa al despliegue (tests, análisis estático,
compileall, etc.).

DESPUÉS
La carga de configuración sensible (env, secrets, credenciales) se ha
desacoplado del import-time y se realiza explícitamente en runtime mediante
una función de inicialización (init_config()).

El módulo puede importarse siempre sin efectos secundarios. La inicialización
del entorno se delega a los entrypoints (wrappers, cronjobs, contenedores),
que son responsables de:
- cargar .env si existe
- leer secrets si están disponibles
- validar precondiciones operativas

Este enfoque:
- elimina fallos en import-time
- permite degradación controlada si faltan dependencias
- hace explícitas las dependencias del sistema
- mejora la portabilidad y la observabilidad de errores

5. PLAN DE MIGRACIÓN PASO A PASO
==========================================
FASE 0 - Congelación de alcance
- Crear docs/MIGRATION_RULES.md
- Crear checklist de validación

FASE 1 – Trabajo paralelo fuera de Git
Se realiza trabajo de refactorización y análisis fuera del repositorio principal
para evitar riesgos sobre el código estable. Se documentan decisiones,
experimentos y cambios estructurales antes de integrarlos en Git.

Resultado:
- Código refactorizado en entorno paralelo
- Decisiones arquitectónicas documentadas (ADR-0000)

FASE 2 – Normalización de imports Python
Se elimina el prefijo artificial "src." de los imports y se adopta una estructura
de paquetes Python coherente, compatible con ejecución mediante python3 -m.

Resultado:
- Imports limpios y coherentes
- src/ tratado como paquete Python real
- Validación con python3 -m compileall en entorno Linux (WSL)

FASE 3 – Consolidación de wrappers operativos
Se establecen wrappers mínimos en scripts/ como única interfaz de ejecución
operativa. Estos wrappers no contienen lógica de negocio y delegan la ejecución
al código Python en src/.

Resultado:
- Separación clara entre infraestructura (scripts/) y lógica (src/)
- Base para ejecución homogénea en host y contenedores

FASE 4 – Normalización de la ejecución de scripts
Toda ejecución de código Python se realiza exclusivamente mediante:

    python3 -m <paquete>.<módulo>

Se eliminan ejecuciones directas de ficheros .py y dependencias implícitas de
PYTHONPATH o rutas absolutas.

Resultado:
- Semántica de ejecución única
- Ejecución reproducible en cualquier entorno

FASE 5 – Auditoría pre-despliegue (sin cambios de código)
Se identifican dependencias operativas, rutas absolutas, servicios externos y
puntos de acoplamiento sin modificar aún el código.

Resultado:
- Lista explícita de precondiciones
- Riesgos operativos documentados

FASE 6 – Cronjobs en contenedores (FINALIZADA)
Se define y adopta el patrón de ejecución de cronjobs dentro de contenedores,
invocando exclusivamente wrappers que llaman a python3 -m <paquete>.<módulo>.
La migración completa se realiza de forma progresiva para minimizar riesgos,
evitando que el host ejecute código Python directamente.

Resultado:
- Cronjobs desacoplados del host
- Ejecución controlada y portable

FASE 7 – Desacoplamiento de configuración y dependencias (FINALIZADA)
Se elimina la carga de configuración sensible en import-time. La lectura de .env,
secrets y dependencias críticas se traslada a runtime mediante una función de
inicialización explícita (init_config()).
Esta fase establece la base obligatoria de inicialización en runtime, aplicada
a todos los entrypoints Python del sistema.

Resultado:
- El código puede importarse en entornos limpios
- Se eliminan crashes en import-time
- La inicialización del entorno pasa a ser responsabilidad del entrypoint

FASE 8 – Endurecimiento y normalización final (FINALIZADA)
Extensión del patrón de desacoplamiento al resto del código:
- lazy imports
- validación de precondiciones
- parametrización de rutas
- documentación operativa definitiva

Resultado esperado:
- Infraestructura robusta
- Comportamiento degradable y observable
- Despliegue seguro en entornos nuevos
