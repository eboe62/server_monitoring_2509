1. OBJETIVO Y ALCANCE
==========================================
Desplegar desde cero server_monitoring_2509 en un droplet DigitalOcean dedicado,
siguiendo el modelo IaC (Infraestructura como Código) definido en el repositorio,
de forma que pueda reproducirse en cualquier otro servidor equivalente.

Prioridad declarada (29/10/2026): versatilidad y portabilidad.
    "La infraestructura debe poder implementarse en cualquier otro servidor."

Incluye:
- Infraestructura Docker por stacks independientes.
- Jobs programados ejecutados exclusivamente en monitoring-cron.
- Persistencia en volúmenes Docker locales.
- Cadena funcional de detección y alerta de seguridad (ver 1.1).
- Stack de observabilidad (Promtail/Loki/Grafana) con carácter didáctico (ver 1.2).

Excluye:
- CI/CD con despliegue automático (CD).
- Alta disponibilidad, multi-nodo y orquestadores (Kubernetes, Swarm).
- Persistencia gestionada externa.
- Honeypot [DECISIÓN 29/10/2026: fuera del alcance del cierre; se retomará
  como micro-stack aislado con ADR propio].
- Migración de datos reales: la BBDD actual es de prueba y sus datos son irrelevantes.

1.1. Cadena funcional de detección (objetivo del proyecto)
    [DECISIÓN 29/10/2026: modelo Python → PostgreSQL; alertas solo vía alert_risk]

    Host (/var/log, solo lectura)
       │  auth.log / fail2ban.log / kern.log
       ▼
    monitoring-cron (supercronic)
       ├─ log_ingestor.log_ingest_batch     → attacking_logs
       ├─ log_ingestor.log_fail2ban_batch   → fail2ban_logs
       ├─ log_ingestor.log_kern_batch       → kern_logs

    Cada ingestor lee solo líneas posteriores al último timestamp guardado en la

    Promtail → Loki → Grafana acompaña al sistema con fines formativos: aprender

2. PRINCIPIOS DEL MODELO IaC
==========================================
2.1. Reglas fundamentales
- El host no ejecuta lógica funcional de aplicación.
- El host sí ejecuta tooling operacional: Docker Compose, auditoría IaC
  (ops/audit/), validaciones estructurales y Makefile.
- Toda lógica de aplicación se ejecuta dentro de contenedores oficiales:
      monitoring-python   (ejecución manual / bajo demanda)
      monitoring-cron     (ejecución programada)
- Todas las tareas programadas del proyecto viven en monitoring-cron
  [DECISIÓN 29/10/2026: monitoring-cron es el responsable de gestionar cualquier cron].
- El código forma parte de las imágenes Docker. Prohibidos los bind mounts de código.
- No se instalan dependencias Python del proyecto en el host.
- El entorno debe poder reconstruirse desde cero con:
      docker system prune -af --volumes  +  make deploy
- El estado del sistema lo definen exclusivamente:
      repositorio versionado + imágenes construidas + volúmenes declarados + secretos locales

2.2. Regla de ejecución Python
    Válido:
        docker exec -it monitoring-python python3 -m log_ingestor.alert_risk
    Prohibido:
        python3 src/log_ingestor/alert_risk.py
        /usr/bin/python3 ...
        cualquier ejecución Python del proyecto desde el host

2.3. Regla de privilegios
- Contenedor autónomo, reproducible y sin dependencias del host → usuario no-root (appuser, UID 10001).
- Contenedor de debugging o herramienta puntual → puede ser root, de forma explícita y temporal.
- Por defecto en todos: cap_drop: ALL + no-new-privileges:true.
- Excepciones (root, capabilities, mounts del host) solo vía ALLOWLIST de ADR-0031
  y ADR-0024 (política de excepciones de privilegio).

2.4. Regla de imágenes
- Cada stack construye su imagen desde una imagen oficial versionada (p. ej. python:3.12-slim).
- No se usan imágenes base internas compartidas (monitoring-base eliminado como patrón).
- Imágenes de terceros fijadas por digest (tag@sha256:...). Prohibido :latest.
- Las imágenes no contienen secretos, .env ni configuración específica de entorno.

2.5. Regla de comunicación
Los servicios solo se comunican mediante:
- redes Docker declaradas (sección 3.3),
- variables de entorno declarativas,
- volúmenes declarados explícitamente.

    - .env: solo variables no sensibles. Versionado únicamente .env.template.

          ops/services/smtp_relay/secrets/smtp_user|smtp_pass
    - Consumo por convención *_FILE (POSTGRES_PASSWORD_FILE, SMTP_USER_FILE...),
      implementada en src/monitoring/common/secrets.py.
    - Permisos: directorio secrets 700, ficheros 600, propietario usuario operativo.
    - Validación: make verify-security

    [PENDIENTE] monitoring-cron no monta el secreto de Postgres ni recibe
    POSTGRES_PASSWORD_FILE ni EMAIL_TO (ver FASE 8).

3.6. Volúmenes y backups
    VOLUMEN (nombre real)          MONTADO EN                     USO
    postgres_postgres-data         monitoring-postgres            datos
    postgres_postgres-backups      monitoring-postgres:/backups   (no recibe backups)
    cron_postgres-backups          monitoring-cron:/backups       destino real de pg_dump
    observability_*-data           loki / grafana / promtail      estado observabilidad
    smtp_relay_smtp_relay_logs     monitoring-smtp-relay          logs SMTP

    Flujo de backup:
        monitoring-cron (5 22 * * *) → scripts/backup_postgres.py
            └ pg_dump -h monitoring-postgres -F c → /backups/monitoring_db-<fecha>.backup

    [PENDIENTE] Los dos compose declaran "postgres-backups" sin "name:"; Docker
    Compose antepone el nombre del proyecto y crea dos volúmenes distintos.
    El comentario "comparte la misma named volume" del compose de cron es falso.

3.7. Política de healthchecks (ADR-0027)
    SERVICE_RUNTIME     readiness real (pg_isready, /ready). Prohibidos checks artificiales.
    SUPERVISOR_RUNTIME  liveness del proceso supervisor (pidof supercronic).
    TOOLBOX_RUNTIME     keepalive o check trivial documentado; no participa en readiness gates.
    INFRA_TRUSTED       el mejor mecanismo que permita la imagen upstream.
    Reglas comunes: ejecutados dentro del contenedor, sin depender del host,
    exit codes reales; excepciones documentadas mediante ADR.

FASE 2B – PERÍMETRO: UFW DENY-BY-DEFAULT                              [PARCIAL]
==========================================
Decisión arquitectónica (PRE-FASE 2B):
Se comparan dos estrategias:

    CRITERIO                    UFW EN HOST                 SOLO CLOUD FIREWALL
    Capas de defensa            dos (proveedor + host)      una
    Error humano en el panel    contenido por el host       exposición directa
    Complejidad                 media                       baja
    Debugging de red            más complejo                más simple
    Defensa en profundidad      sí                          limitada

    Adoptado: UFW activo en el host con política deny-by-default.

Momento: después de instalar Docker y antes de desplegar el repositorio, para que
no exista ninguna ventana temporal sin política de red.

Acciones (orden estricto, para no perder el acceso SSH):
        sudo ufw allow OpenSSH
        sudo ufw enable

Política resultante:
        Default: deny (incoming), allow (outgoing), deny (routed)

Puertos autorizados:
        22/tcp   SSH
        80/443   solo si existe un servicio público que los use

PostgreSQL: nunca se publica, ni siquiera restringido por IP. Acceso solo por
red Docker, docker exec o túnel SSH temporal.

Didáctico – Docker puede saltarse UFW:
    Docker inserta sus propias reglas iptables al publicar un puerto (-p 8080:80).
    Ese puerto queda accesible desde Internet aunque UFW no lo permita.
    Conclusiones:
    - UFW no sustituye la disciplina en los compose.
    - Por eso la regla de 3.4: solo 127.0.0.1:<puerto> o ningún puerto publicado.
    - La seguridad depende de la coherencia compose + UFW + firewall del proveedor.

Didáctico – ejemplo real de estado incorrecto corregido (histórico):
    [2] 80,443,3000,3100,5432,5433/tcp ALLOW IN Anywhere
    y una regla temporal 5432/tcp ALLOW IN <ip>  → ambas eliminadas (sudo ufw delete N).

Validación:
        sudo ufw status verbose
        sudo ss -tulpn

Estado (StatusQuo 261029):
    UFW activo, deny-by-default; reglas 22, 80 y 443 (IPv4/IPv6).
    Solo sshd escucha en 0.0.0.0; Loki y Grafana en 127.0.0.1.
    [PENDIENTE] 80/443 abiertos sin ningún servicio detrás. Con el honeypot fuera
                del alcance, deben cerrarse:
                    sudo ufw delete allow 80/tcp

FASE 4 – CONFIGURACIÓN DE ENTORNO (pre-runtime)                        [CERRADA]
==========================================
Objetivo: dejar cada stack listo para arrancar, sin ejecutarlo todavía.

4.1. Micro-stacks (ops/services/<servicio>/)
    Cada uno debe:
    - construirse y desplegarse de forma independiente;
    - poder copiarse a otro repositorio sin perder funcionalidad;
    - usar solo archivos de su propio directorio (build context propio);
    - gestionar su propio .env.template, secrets/ y volúmenes.
    Estructura mínima:
        ops/services/<servicio>/
        ├── compose.yml
        ├── Dockerfile        (si aplica)
        ├── .env.template
        ├── secrets/          (no versionado, salvo .gitkeep)
        ├── config/           (si aplica)
        └── scripts/          (si aplica)

4.2. Infra-stacks (ops/stacks/<stack>/)
    - Pueden usar build context superior (necesitan src/ y requirements.txt).
    - Pueden montar rutas del host solo si están aprobadas en la ALLOWLIST (ADR-0031).
    - NO pueden montar docker.sock (ADR-0018).
    - NO pueden depender de bind mounts de código: el código va en la imagen.

4.3. Variables y secretos
    Por servicio: .env.template versionado → .env real generado a mano (en .gitignore).
    Secretos en ficheros (3.5). Ejemplo para Postgres:
        mkdir -p ops/services/postgres/secrets && chmod 700 ops/services/postgres/secrets
        printf '%s' '<password>' > ops/services/postgres/secrets/postgres_password
        chmod 600 ops/services/postgres/secrets/postgres_password

APÉNDICE A – REGISTRO DE HALLAZGOS Y LECCIONES APRENDIDAS
==========================================
Cada entrada: hallazgo → causa → resolución → lección.

A.1. pytz ausente en monitoring-cron (16-17/08/2026)              [RESUELTO]
    log_fail2ban_batch fallaba cada 10 min con ModuleNotFoundError.
    Causa: dependencia no declarada en requirements.txt (único uso en el proyecto).
    Resolución: pytz añadido; imagen reconstruida; verificado con docker exec (commit 954164f).
    Lección: un job programado puede fallar en silencio durante meses si nadie
    revisa sus logs → motivación de la "alerta de silencio" (FASE 12).

A.2. Test de red que nunca podía fallar (17/08/2026)              [RESUELTO]
    test-resilience-network imprimía "[FAIL]" seguido de "[OK]" y continuaba.
    Causa: "|| (echo ... && exit 1)". exit dentro de ( ) solo termina el subshell,
    no el script. Afectaba a los 4 chequeos del target.
    Resolución: "|| { echo ...; exit 1; }" (el brace group se ejecuta en el mismo shell).
    Efecto colateral: al poder fallar, apareció un segundo defecto: el test esperaba
    que monitoring-python pasara a "unhealthy", imposible porque su healthcheck es
    trivial por diseño (TOOLBOX_RUNTIME). Se eliminaron esas esperas y se mantuvieron
    las comprobaciones TCP (nc -z), que son la señal correcta (commit c28bb3d).
    Lección: un test que nunca falla puede ocultar otros defectos. Hay que provocar
    el fallo a propósito al menos una vez.

A.3. Promtail sin healthcheck (16-17/08/2026)                      [RESUELTO]
    Su política declarada exigía readiness, pero la imagen upstream no incluye
    wget, curl, nc, pgrep ni ps; solo grep.
    Resolución: liveness por /proc ("grep -q promtail /proc/1/comm"), tras confirmar
    que promtail es el PID 1. Política cambiada a liveness, igual que smtp-relay (commit 3a97150).
    Verificado healthy en el StatusQuo 261029.
    Lección: la política de healthcheck debe adaptarse a lo que la imagen permite
    (por eso la tipología INFRA_TRUSTED).

A.4. SMTP relay más restrictivo que lo documentado (16/08/2026)   [RESUELTO]
    El documento esperaba 127.0.0.1:2526->587; el compose no publica ningún puerto.
    Se corrigió el documento, no el sistema: era menor exposición, no un defecto.

A.5. setup_symlinks.sh con ruta base inexistente (17/08/2026)     [RESUELTO]
    BASE_DIR apuntaba a /opt/monitoring/resource_monitor, sin ninguno de los scripts.
    Sustituido por rutas explícitas por script.
    (Su utilidad queda sujeta a la revisión de 5.3.)

A.6. Falso positivo "Secrets versionados: secrets.py" (18/08/2026) [ACEPTADO]
    secrets.py es el cargador seguro *_FILE y no contiene valores. El heurístico

A.7. Volúmenes "compartidos" que no lo son (29/10/2026)           [PENDIENTE]
    Dos compose declaran "postgres-backups" sin name: → cron_postgres-backups y
    postgres_postgres-backups.
    Lección: un named volume sin name: explícito lleva delante el nombre del proyecto
    Compose (por defecto, el directorio). Para compartirlo entre stacks: name:
    explícito o external: true.

A.8. "$$" en un script bash (29/10/2026)                          [PENDIENTE]
    audit_repo_host.sh:297 → grep -q "^$c$$". En un Makefile "$$" escapa "$";
    en bash es el PID del proceso. La expresión nunca coincide.
    Lección: la sintaxis copiada entre Makefile y shell cambia de significado.
