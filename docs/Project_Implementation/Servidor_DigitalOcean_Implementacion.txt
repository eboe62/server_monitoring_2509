1. OBJETIVO Y ALCANCE
==========================================
Desplegar desde cero el proyecto server_monitoring_2509 en un droplet
DigitalOcean dedicado, siguiendo el modelo IaC (Infrastructure as Code) definido en el repositorio.

Incluye:
- Infraestructura Docker
- Cronjobs vía contenedor
- Observabilidad
- Persistencia mediante volúmenes Docker

Modelo de persistencia:
    La persistencia de datos se basa exclusivamente en volúmenes Docker locales al droplet. No se emplea almacenamiento externo ni servicios gestionados de base de datos.

Modelo de recuperación
    La recuperación ante desastre se apoya en:
    - Recreación declarativa completa desde repositorio versionado.
    - Reconstrucción de contenedores a partir de Dockerfiles y docker-compose declarativos.
    - Restauración lógica de datos mediante backups lógicos PostgreSQL.
    - Volúmenes Docker persistentes como única fuente de estado.

    Backups lógicos PostgreSQL:
        Ejecutados desde el runtime contenerizado mediante monitoring-cron.
        Flujo conceptual:
            monitoring-cron
                └ pg_dump -h postgres
        Los backups se almacenan en:
            /ops/backups

    Snapshots del droplet:
        Se consideran únicamente mecanismo de contingencia a nivel de infraestructura y no sustituyen los backups lógicos.
        - No constituyen dependencia estructural del modelo.
        - No sustituyen la reproducibilidad declarativa.
        - No eximen de validar reconstrucción completa desde cero.

    El entorno debe poder reconstruirse íntegramente sin necesidad de snapshot previo.
    Este modelo es una decisión consciente del alcance PRO.

Excluye explícitamente:
- Cambios de código
- Refactorizaciones
- Nuevas funcionalidades
- CI/CD automático

PRINCIPIO FUNDAMENTAL:

El entorno PRO sigue estrictamente Infraestructura como Código (IaC):

- El host no ejecuta lógica funcional de aplicación.
- El host puede ejecutar tooling operacional asociado a:
    - Docker Compose
    - auditoría IaC
    - validaciones estructurales
    - comprobaciones runtime
    - automatismos declarativos del entorno
- El host mantiene el control-plane operacional del entorno Docker Compose standalone.
- No se permite instalar dependencias Python globales asociadas al proyecto.
- No se permite ejecutar scripts del proyecto directamente desde el host.
- No se permite el uso de:
    python3 script.py
    /usr/bin/python3 ...
    fuera de contenedores oficiales del proyecto.
- Toda ejecución de código debe ocurrir exclusivamente dentro de:
    monitoring-python
    monitoring-cron
- monitoring-python actúa como bridge funcional controlado entre:
    backend
    observabilidad
    Y eso tiene sentido arquitectónico:
    - necesita enviar logs/métricas
    - necesita hablar con postgres
- Los contenedores runtime deben contener internamente todo el código necesario para su ejecución.
    No se permite dependencia estructural de bind mounts del host para lógica de aplicación.
- La reconstrucción completa del entorno debe ser posible tras:
    docker system prune -af --volumes
- Esta validación forma parte obligatoria del modelo IaC del proyecto.
- No se permiten ejecuciones manuales de lógica funcional fuera del modelo declarativo.
- Se permiten automatismos host-side declarativos destinados exclusivamente a:
    - auditoría
    - validación
    - orquestación
    - tooling operacional

Cualquier desviación invalida el modelo IaC del entorno PRO.

No pretendemos un modelo "monolito Docker con modularización parcial” sino un modelo híbrido controlado estructurado en tres planos de arquitectura claramente diferenciados:

PLANO 1 – Aplicación (Micro-Stacks Autónomos)
    - Servicios desacoplados.
    - Despliegue independiente.
    - Autonomía estructural completa.
    - Segmentación de red explícita según responsabilidad funcional. Ejemplos:
        PostgreSQL → backend-net
        SMTP-Relay → restricted-net

PLANO 2 – Runtime Interno (Infra-Stacks)
    - Servicios internos del entorno.
    - Comparten código versionado cuando aplica.
    - No son autónomos a nivel arquitectónico/exportable.
    - Sí deben ser autónomos a nivel runtime y reproducibilidad operacional.
    - Se comunican exclusivamente mediante redes explícitamente segmentadas. Ejemplos:
        monitoring-python → backend-net + observability-net
        monitoring-cron → backend-net
        observability → observability-net

PLANO 3 – Seguridad del Host
    - Componentes nativos del sistema operativo.
    - No ejecutan lógica de aplicación.
    - Refuerzan el perímetro y el acceso.
    - Ejemplos: UFW, fail2ban, automatismos declarados.

MODELO DE EJECUCIÓN DE CONTENEDORES:
- Los contenedores del runtime deben ser autónomos, reproducibles y desacoplados del host.
- No deben depender de bind mounts de código ni de rutas externas al contenedor.
- Deben ejecutar un único proceso claramente definido y controlado.

Regla de privilegios:
- Si un contenedor es:
    - autónomo
    - reproducible
    - sin dependencias del host
    → Debe ejecutarse como usuario no-root (ej: appuser).

- Si un contenedor es:
    - interactivo
    - de debugging
    - herramienta operativa puntual
    → Puede ejecutarse como root de forma controlada y explícita.

Esta distinción es obligatoria para mantener coherencia entre seguridad, reproducibilidad y operabilidad.

Cada plano tiene responsabilidades diferenciadas y no debe introducir dependencias estructurales cruzadas que violen el modelo IaC adoptado.

La plataforma adopta el modelo de red única con segmentación explícita de redes Docker:

Definición operativa del modelo micro-stack autónomo:
Cada Micro-Stack:
- Tiene su propio docker-compose.yaml
- Puede construirse y desplegarse de forma independiente
- Gestiona sus propios secrets y .env.template
- Declara sus propios volúmenes
- No introduce dependencias estructurales en el Infra-Stack
- Contiene su propio Dockerfile (si aplica)

El Infra-Stack agrupa servicios internos operativos.

Cada servicio:
- Define su propia imagen
- No comparte imagen base obligatoria
- Puede duplicar runtime si es necesario para mantener aislamiento y reproducibilidad

Modelo de ejecución de jobs (CRON)
    Todos los jobs programados se ejecutan dentro del contenedor:
        monitoring-cron
    Scheduler:
        supercronic
    Restricciones:
        - El host no ejecuta crontabs del proyecto.
        - Los jobs se ejecutan mediante:
            python3 -m paquete.modulo
        Ejemplo:
            python3 -m log_ingestor.alert_risk

PostgreSQL es considerado como un micro-stack autónomo de estado, con las siguientes reglas adicionales:
- No se expone públicamente
- Declara su propio volumen persistente
- Puede migrarse de servidor mediante dump lógico
- No depende estructuralmente de otros servicios

La comunicación entre servicios se realiza exclusivamente a través de:
- Redes Docker explícitamente declaradas según el dominio funcional:
    backend-net
    observability-net
    restricted-net
- Variables de entorno declarativas
- Volúmenes explícitamente definidos

No se utilizará imágenes base comunes internas (p.e. monitoring-base python) porque dificulta la validación en CI/CD

Por lo tanto cada stack debe construir su imagen directamente desde una imagen oficial versionada (ej. python:3.12-slim).

Condiciones obligatorias:
Debe contener exclusivamente:
- Runtime común
- Dependencias compartidas
- Código fuente versionado

No puede contener:
- Secrets
- .env
- Configuración específica de servicio
- Variables de entorno de producción
- Lógica de aplicación específica

Restricciones adicionales:
- No se permite el uso de imágenes base internas compartidas.
- No se permite dependencia entre stacks a nivel de build.
- Cada stack debe ser completamente autónomo en su construcción.

Cada servicio debe poder:
- Sustituir monitoring-base por otra base compatible.
- Extender una imagen oficial externa sin romper la arquitectura declarativa.
monitoring-base es una optimización de build, no un componente arquitectónico estructural.

El principio de autonomía prevalece sobre la conveniencia de reutilización.

REGLA ARQUITECTONICA:
- Ningún archivo Python se ejecuta por ruta absoluta.
- Siempre se ejecuta mediante: python3 -m paquete.modulo

Comando válido:
docker exec -it monitoring-python python3 -m log_ingestor.alert_risk

Comando prohibido:
python3 src/log_ingestor/alert_risk.py
/usr/bin/python3 ...

monitoring-python está clasificado oficialmente como:
    TOOLBOX_RUNTIME

Su función es:
- proporcionar entorno runtime persistente de la aplicación
- permitir ejecución controlada de scripts internos de negocio mediante docker exec
- procesar utilidades en diferido que requieran interactuar con el ecosistema de persistencia

No representa:
- API runtime expuesta externamente
- servicio HTTP
- daemon de automatización de infraestructura o auditoría IaC (responsabilidad exclusiva del host)

Por tanto:
- no requiere readiness HTTP
- puede utilizar keepalive explícito
- puede utilizar healthcheck trivial documentado

Este comportamiento es intencional y NO constituye desviación
arquitectónica.

2. POLÍTICA OFICIAL DE HEALTHCHECKS
==========================================

Los healthchecks Docker deben alinearse con la función arquitectónica
real de cada contenedor.

El entorno PRO NO asume que todos los contenedores representan
microservicios HTTP clásicos.

REGLAS OFICIALES:

2.1. SERVICE_RUNTIME
   Requieren readiness checks reales.

   Los checks deben validar:
   - disponibilidad funcional
   - aceptación de conexiones
   - operatividad semántica del servicio

   Ejemplos válidos:
   - pg_isready
   - HTTP /ready
   - HTTP /api/health

2.2. SUPERVISOR_RUNTIME
   Requieren liveness checks de proceso supervisor.

   Ejemplos válidos:
   - pidof supercronic
   - pgrep master

2.3. TOOLBOX_RUNTIME
   Pueden:
   - no tener healthcheck
   - utilizar keepalive explícito
   - utilizar healthchecks triviales documentados

   Estos contenedores:
   - NO representan servicios funcionales
   - NO deben participar en readiness gates
   - NO deben bloquear CI/CD por ausencia de readiness

2.4. INFRA_TRUSTED
   Deben utilizar el mecanismo más apropiado según:
   - servicio real
   - capacidades upstream
   - endpoints disponibles

RESTRICCIONES:
- Se prohíben healthchecks artificiales en SERVICE_RUNTIME.
- Los healthchecks NO deben depender del host.
- Los healthchecks deben ejecutarse dentro del runtime contenerizado.
- Los checks deben devolver exit codes reales y deterministas.
- Las excepciones deben documentarse mediante ADR.

OBSERVACIÓN:
Un healthcheck trivial puede considerarse válido únicamente cuando el contenedor esté explícitamente  clasificado como TOOLBOX_RUNTIME.

==========================================
PRE-FASE 2B - DECISIÓN ARQUITECTÓNICA DE PERÍMETRO: UFW EN HOST
==========================================
Motivación
El modelo IaC adoptado establece que el host no ejecuta lógica de aplicación y actúa exclusivamente como orquestador de contenedores Docker.
Sin embargo, esto no elimina la necesidad de control de perímetro a nivel de sistema operativo.

Se evalúan dos estrategias principales:
A.- Confiar únicamente en:
    - Security Groups del proveedor (DigitalOcean)
    - Reverse proxy (si aplica)
    - No exponer servicios sensibles
B.- Activar firewall local en el host (UFW) con política deny-by-default.

Comparativa resumida:
CRITERIO                          | UFW ACTIVADO EN HOST                    | SOLO SECURITY GROUP + REVERSE PROXY
----------------------------------|-----------------------------------------|------------------------------
Capa de seguridad                 | Doble capa (provider + host)            | Única capa (provider)
Protección ante error Docker -p   | Parcial (si reglas coherentes)          | Depende 100% del security group
Riesgo de exposición accidental   | Menor si disciplina correcta            | Mayor si se abre puerto en DO
Complejidad operativa             | Media                                   | Baja
Debugging de red                  | Más complejo (iptables + ufw + docker)  | Más simple
Coherencia con hardening formal   | Alta                                    | Media
Defensa en profundidad            | Sí                                      | Limitada
Rendimiento                       | Impacto despreciable                    | Impacto despreciable
Modelo profesional producción     | Recomendado                             | Aceptable en entornos simples

Decisión adoptada
- Se adopta el modelo: "UFW activado en host con política deny-by-default"

Reglas base:
- Default: deny incoming
- Allow:
    22/tcp (SSH)
    80/tcp (HTTP) si aplica
    443/tcp (HTTPS) si aplica
- PostgreSQL NO se expone públicamente
- Cualquier apertura adicional requiere justificación explícita

Recomendación razonada
- Añade una segunda capa de defensa independiente del proveedor.
- Reduce impacto de errores humanos en Security Groups.
- Aísla servicios Docker que accidentalmente publiquen puertos.
- Refuerza coherencia con modelo de micro-stacks autónomos.
- Mantiene el principio de mínimo privilegio.

Advertencia crítica
Docker manipula iptables/nftables dinámicamente.
El firewall debe activarse únicamente:
- Tras instalar Docker
- Tras verificar que el daemon está operativo
- Con política explícita definida

Un firewall mal configurado puede:
- Bloquear tráfico legítimo entre contenedores
- Interferir con reglas NAT creadas por Docker
- Provocar pérdida de acceso SSH si no se permite previamente

Por tanto:
    sudo ufw allow OpenSSH
    sudo ufw enable

Debe ejecutarse en ese orden estricto.
Momento de ejecución en el plan

Antes del despliegue del repositorio (FASE 3) y antes de cualquier runtime productivo.

Esto garantiza que:

Objetivo

Momento de ejecución

2B.1. Activación controlada de UFW
Antes de activar el firewall debe permitirse explícitamente el acceso SSH:
    sudo ufw allow OpenSSH

Esta regla habilita el tráfico entrante por el puerto 22 (IPv4/IPv6) y es obligatoria antes de ejecutar la activación de UFW, ya que garantiza la continuidad del acceso administrativo remoto bajo una política restrictiva.

Orden estricto de ejecución:
    sudo ufw allow OpenSSH
    sudo ufw enable

Durante la activación puede mostrarse una advertencia indicando que la conexión SSH podría interrumpirse.
Si la regla "OpenSSH" fue configurada previamente, la activación puede confirmarse con seguridad.

2B.2. Política resultante:
    Tras la activación, el estado esperado es:
    Default deny (incoming)
    Default allow (outgoing)
    Default deny (routed)

Esto implica:
    Todo tráfico entrante no autorizado explícitamente queda bloqueado.
    El servidor puede iniciar conexiones salientes (updates, pulls, etc.).
    El host no actúa como router entre interfaces.

Verificación:
    sudo ufw status verbose

    Resultado esperado:
        Status: active
        Logging: on (low)
        Default: deny (incoming), allow (outgoing), deny (routed)

2B.3. Puertos autorizados a nivel de host
Unicamente se autorizan los siguientes puertos:
    22/tcp → SSH
    80/tcp → HTTP (si aplica)
    443/tcp → HTTPS (si aplica)

Ejemplo de habilitación explícita:
    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

2B.4. Restricción explícita sobre PostgreSQL:
    PostgreSQL NO se expone en el host.

    Reglas:
        - El puerto 5432 NO se publica.
        - No se permite apertura directa del puerto, ni siquiera restringida por IP.
        - PostgreSQL es accesible exclusivamente a través de la red Docker interna (redes monitoring-network Makefile).
        - El acceso se realiza exclusivamente mediante:
            Red Docker interna (redes monitoring-network)
            SSH al host + docker exec
            Túnel SSH temporal (si fuera imprescindible)
        - Cualquier excepción requiere ADR explícito documentado.

La activación del firewall se realiza:
    Tras validar que Docker está operativo, para evitar interferencias con las reglas de red gestionadas por el daemon Docker
    Antes del despliegue del repositorio (FASE 3).

2B.6. Consideraciones técnicas sobre Docker
Docker gestiona reglas propias en iptables cuando se publican puertos mediante la opción:
    -p host:container

Estas reglas se insertan directamente en las cadenas de filtrado del sistema, pudiendo permitir el acceso externo a un puerto aunque no exista una regla explícita en UFW que lo autorice.

Por ejemplo, si se lanza un contenedor utilizando:

    -p 8080:80

Docker creará automáticamente las reglas necesarias para exponer el puerto 8080 del host hacia el servicio interno del contenedor.
En este escenario, el puerto 8080 quedará accesible desde el exterior aunque no exista una regla específica en UFW permitiendo dicho puerto.

Esto implica dos consideraciones técnicas fundamentales:

- Bypass de UFW: Docker puede exponer servicios al exterior mediante la publicación explícita de puertos (-p host:container), independientemente de la configuración declarativa de UFW.
- Falsa sensación de seguridad: La existencia de reglas restrictivas en UFW no garantiza, por sí sola, que un puerto permanezca inaccesible si Docker lo ha publicado directamente.

Por tanto:
- No se deben publicar puertos sensibles en docker-compose.
- UFW no sustituye la disciplina declarativa.
- La seguridad depende de coherencia entre:
    docker-compose
    reglas UFW
    Security Groups del proveedor.

2B.7. Política de exposición de puertos Docker
Por defecto, los contenedores del proyecto NO deben publicar puertos hacia el host.

Regla de exposición de puertos:
    - Micro-stacks:
        No deben declarar ports

    - Servicios internos accesibles desde el host:
        Deben usar bind explícito a loopback:
        127.0.0.1:<host_port>:<container_port>

    - Servicios públicos:
        Solo 80 y 443 pueden exponerse en el host

La comunicación entre servicios debe realizarse exclusivamente mediante:
    - redes Docker internas
    - resolución DNS interna de Docker

Cuando sea necesario exponer un servicio al host, debe aplicarse una restricción explícita de interfaz:
    127.0.0.1:<puerto_host>:<puerto_contenedor>

Ejemplo permitido:
    ports:
        - "127.0.0.1:3001:3001"

Ejemplo prohibido:
    ports:
        - "3001:3001"

La exposición sin restricción de interfaz provoca que Docker publique el servicio en todas las interfaces del host.

Servicios considerados internos que NO deben exponerse por defecto:
    - PostgreSQL
    - Promtail
    - contenedores de runtime interno

Excepciones controladas:
    - Loki puede exponerse exclusivamente en loopback (127.0.0.1) para tareas de debugging, testing o validación operativa, siempre que no exista exposición pública.
    - Esta excepción debe considerarse temporal o justificada.

Servicios que pueden exponerse bajo justificación:
    - Grafana
    - servicios de administración explícitamente documentados

Esta política complementa el firewall UFW y reduce el riesgo de exposición accidental.

FASE 4 – CONFIGURACIÓN DE ENTORNO: Modelo Micro-stack Autónomo (Pre-runtime estructural)

4.1. Definición de MICRO-STACKS AUTONOMO:
Se consideran Micro-Stacks Autónomos aquellos servicios ubicados en:
    ops/services/<servicio>/

Cada Micro-Stack debe:
    - Ser construible y desplegable de forma independiente.
    - Poder copiarse a otro repositorio sin perder funcionalidad.
    - Construirse utilizando exclusivamente archivos contenidos dentro de su propio directorio.
    - No depender estructuralmente de archivos externos al servicio.

No se permite dependencia estructural de runtime común entre stacks.
    Cada Micro-Stack o Infra-Stack debe:
    - Definir su propio runtime (ej. Python)
    - Gestionar sus propias dependencias
    - Ser construible de forma autónoma

La reutilización de imágenes base internas queda eliminada como patrón arquitectónico.

Restricciones aplicables a Micro-Stacks
No se permite:
    - Dependencia de archivos fuera de ops/services/<servicio>/.
    - Uso de build context superior al directorio del servicio.
    - Montaje de rutas absolutas del host como dependencia estructural.

Estructura mínima obligatoria
Cada Micro-Stack debe contener como mínimo:
Estructura mínima obligatoria
Cada Micro-Stack debe contener como mínimo:

ops/services/<servicio>/
├── docker-compose.yaml
├── Dockerfile
├── .env.template
├── config/
├── scripts/

Notas:
- No se utiliza directorio secrets/ en el modelo actual.
- Las credenciales se gestionan exclusivamente mediante variables
  de entorno definidas en archivos .env no versionados.

4.2. Definición de INFRA-STACKS (infraestructura Operativa):
Se consideran Infra-Stacks aquellos servicios definidos en:
    ops/docker/
    Ejemplos:
    - monitoring-python
    - monitoring-cron
    - observability

Estos forman parte del runtime interno del entorno y no son Micro-Stacks autónomos a nivel arquitectónico/exportable y, por lo tanto:
    - Deben mantenerse coherentes como unidad de runtime interno.
    - Pueden usar build context superior
    - Pueden montar rutas del host justificadas
    - Pueden acceder al socket Docker
    - Pueden acceder a logs del host

No obstante:
    - NO pueden depender de bind mounts estructurales para ejecutar código
    - El código operativo debe existir dentro de la imagen Docker
    - Deben poder reconstruirse desde cero tras:
        docker system prune -af --volumes

Por tanto:
    - NO son autónomos como unidad exportable/reutilizable
    - PERO sí deben ser autónomos a nivel runtime/ejecución

No obstante, deberán:
    - Declarar redes monitoring-network (Makefile) como external: true
    - No versionar secretos
    - No incluir secretos dentro de la imagen

Notas:
Algunos contenedores de infraestructura requieren acceso al socket Docker del host (/var/run/docker.sock). Este acceso debe limitarse exclusivamente a infra-stacks y considerarse equivalente a privilegios administrativos sobre el host Docker.

4.3. Gestión de variables de entorno y secretos:
Por cada servicio:
    - Debe existir .env.template versionado.
    - El archivo real .env se genera a partir de la plantilla.
    - .env debe estar incluido en .gitignore.

Modelo actual (Docker Compose v2 sin Swarm):
    - No se utilizará Docker Swarm secrets.
    - No se permite el uso de "secrets: external: true".
    - No se permite el uso implícito de Docker Swarm como mecanismo de gestión de secretos.

Las credenciales deben gestionarse exclusivamente mediante:
    - Variables de entorno definidas en archivos .env no versionados.

Reglas obligatorias:
    - Debe existir un archivo .env.template versionado.
    - El archivo real .env se genera manualmente a partir de la plantilla.
    - .env debe estar incluido en .gitignore.
    - Los valores reales nunca deben aparecer en el repositorio.

No se utiliza:
    - Docker Swarm secrets
    - directorios secrets/
    - mecanismos de gestión de secretos externos

Si en el futuro se adopta Swarm u otro orquestador, deberá formalizarse mediante ADR específico.

4.4. Separación Import-Time / Run-Time
Debe garantizarse que la configuración sensible no forme parte de las imágenes Docker.

Comprobar que:

    - Las imágenes Docker NO deben contener carpeta secrets/

Validación por servicio

Cada servicio debe construir su propia imagen de forma autónoma.

Solo se permite:

Condiciones para utilizar imagen base (modularidad monitoring-base) interna:

4.6. Infraestructura de Red (Red Docker):
Se desestima la declaración de una red externa común a todos los stacks adoptando el modelo de red única con segmentación explícita de redes Docker:
Objetivos:
- reducir movimiento lateral
- minimizar superficie de exposición
- mejorar capacidad forense
- evitar contaminación cruzada entre stacks.

La plataforma adopta el modelo de red única con segmentación explícita de redes Docker:
    backend-net
    Comunicación interna de aplicación y persistencia.
    Uso previsto:
    - monitoring-python
    - monitoring-cron
    - postgres

    observability-net
    Plano de observabilidad y logging.
    Uso previsto:
    - grafana
    - loki
    - promtail
    - monitoring-python (solo si requiere acceso a Loki)

    restricted-net
    Servicios con aislamiento reforzado o egress controlado.
    Uso previsto:
    - smtp-relay
    - contenedores temporales de debugging controlado

Las redes se declaran en cada docker-compose:
    networks:
        external: true

Reglas:
    - La red se crea explícitamente una única vez por host.
    - La red puede eliminarse durante operaciones de limpieza profunda:
        docker system prune -af --volumes
    - Todo proceso de reconstrucción completa debe re-crear explícitamente la red compartida antes del despliegue.
        Bootstrap oficial:
            make monitoring-networks
        Validación:
            make test-network
    - Validación sintactica:
        docker compose -f ops/docker/docker-compose.observability.yml config
    - No se permite depender del project-name implícito de Docker Compose.
    - Se prohíbe el uso de redes generadas automáticamente.

El stack de observabilidad opera exclusivamente sobre observability-net.
Excepciones explícitas:
    - monitoring-python puede conectarse adicionalmente a observability-net si requiere ingestión o consulta de logs.
    - Grafana no debe conectarse a backend-net salvo necesidad documentalmente justificada.

Validación:
    - docker network inspect <red>
    - Confirmar ausencia de redes prefijadas tipo <project>_<red>

5.8 – Modelo de validación de resiliencia:
La resiliencia se valida mediante simulaciones controladas de fallo real:
- Fallo interno de contenedor:
    Terminación del proceso principal (PID 1) para validar restart policy.
- Fallo de dependencia:
    Parada del servicio PostgreSQL y validación de pérdida real de conectividad (DNS + TCP).
- Fallo de red:
    Desconexión de la red Docker para validar degradación y recuperación.
- Observabilidad:
    Generación de logs y validación de ingestión en Loki.

Estos tests reflejan el comportamiento real de Docker Compose (single-node, sin orquestador), según ADR-0017, y no asumen capacidades de self-healing propias de Kubernetes. Asimismo, la recolección de datos de HostConfig mediante docker inspect actúa en esta fase como un baseline de evidencia estrictamente observacional, posponiendo la lógica de diff estructurado automático para hitos posteriores.

Nota:
Esta fase no introduce despliegue automático (CD), sino validación previa obligatoria antes de cualquier promoción de cambios.

Estado verificado y defecto de test detectado (StatusQuo 260816):
    Durante la ejecución de `make test-resilience-completo` se observó un
    patrón anómalo en el paso de fallo de red: se imprime "[FAIL] no degrada
    por red" inmediatamente seguido de "[OK] degradación por red OK", y el
    test continúa como si hubiera pasado. Localizado el código exacto en el
    target `test-resilience-network` del Makefile:

        timeout 60 sh -c '...' || (echo "[FAIL] no degrada por red" && exit 1); \
        echo "[OK] degradación por red OK"; \

    El `exit 1` está dentro de un subshell `(...)`; en shell, `exit` dentro
    de `(...)` solo termina ese subshell, no el script que lo contiene. Por
    tanto, aunque el chequeo de degradación falle o expire por timeout, la
    ejecución continúa igualmente a la línea siguiente, que imprime "[OK]"
    de forma incondicional. Este paso del test NUNCA puede reportar un
    fallo real, independientemente del comportamiento real del sistema —
    explica el comportamiento "no determinista" ya señalado en PRIORIDAD 11
    del documento de Corrección.

    Al revisar el resto del Makefile se confirmó que el mismo patrón se
    repetía 4 veces dentro de este mismo target (aislamiento de red,
    degradación por red, recuperación TCP, recuperación por health) — es
    decir, ninguno de los 4 chequeos de este target podía fallar realmente.
    Las otras 4 apariciones del patrón `|| (echo ... && exit 1)` en el
    Makefile (comprobación de HostConfig, relay SMTP, Loki) son líneas de
    recipe independientes sin continuación `\`, por lo que en esas el
    subshell no atrapa nada — no comparten el defecto.

    Corregido (17/08/2026): las 4 ocurrencias dentro de
    `test-resilience-network` sustituidas de `(echo "..." && exit 1)` a
    `{ echo "..."; exit 1; }` — un brace group corre en el mismo shell, por
    lo que el `exit` sí se propaga y detiene el recipe correctamente.

    Hallazgo derivado (17/08/2026): al arreglar lo anterior, el pipeline de
    CI empezó a fallar realmente en el paso "esperando degradación (health)".
    Causa raíz: el healthcheck de monitoring-python (scripts/healthcheck.py)
    es deliberadamente trivial (`sys.exit(0)` incondicional, comentario
    explícito "evita falsos negativos en CI") — nunca puede reportar
    `unhealthy`, así que esperar ese estado es una condición imposible por
    diseño, no un problema de timing. El bug de subshell llevaba años
    enmascarando este segundo problema.

    Decisión: eliminados ambos pasos de espera de healthcheck de Docker
    ("esperando degradación (health)" y su simétrico "esperando recuperación
    (health)"), ya que ambos dependían de un healthcheck que nunca cambia de
    estado. El target conserva las comprobaciones TCP directas (`nc -z`)
    que ya validaban aislamiento y recuperación reales, y que son la señal
    correcta para este propósito. Actualizado también el comentario de
    cabecera del target para reflejar el comportamiento real.

    @reboot /scripts/apply_ssh_ratelimit.sh > /var/log/apply_ssh_ratelimit.log 2>&1

    - Los cron del host no ejecutan lógica de aplicación.
    - Los cron del host no ejecutan módulos Python del proyecto.
    - Los cron del host no sustituyen el scheduler interno del sistema.

    La ejecución periódica de tareas del proyecto se realiza mediante un contenedor dedicado:
        monitoring-cron

        ops/cron/monitoring.cron

    No se permite:
    - Configuración manual directa de iptables.
    - Introducir tareas persistentes no documentadas.

Nota: No se realiza configuración directa de iptables. El filtrado de tráfico se gestiona mediante UFW como capa de abstracción soportada por el sistema operativo, y por Docker, que administra dinámicamente las reglas necesarias  para la comunicación entre contenedores. 8.0. Estado verificado y defecto activo (StatusQuo 260816)
    Hallazgo: el job `log_fail2ban_batch` (programado cada 10 minutos) falla
    en cada ejecución desde el arranque del contenedor monitoring-cron, con
    el siguiente error confirmado en `docker logs monitoring-cron`:

        ModuleNotFoundError: No module named 'pytz'
        (File "/opt/monitoring/src/log_ingestor/log_fail2ban_batch.py", line 6,
         in <module> ... import pytz)

    Alcance no determinado: no se ha confirmado si el defecto afecta
    únicamente a log_fail2ban_batch o también a otros jobs de log_ingestor
    que puedan compartir la misma dependencia o cadena de importación.
    Determinar el alcance exacto es el primer paso obligatorio antes de
    cualquier corrección de código.

    Relación con la pausa de migración de FASE 6.0: este defecto es
    INDEPENDIENTE de la pausa de migración de tablas documentada en 6.0. El
    fallo ocurre en la línea de `import pytz`, antes de que el script llegue
    a ejecutar lógica alguna o a intentar tocar la base de datos — por tanto
    no depende de si `monitoring_db` tiene tablas o no, y no debe esperar a
    que se levante dicha pausa para corregirse.

    Nota anticipada (hipótesis, no confirmada): una vez corregida la
    dependencia `pytz`, es razonablemente esperable que el job pase a fallar
    por un error distinto del tipo "relation ... does not exist" si
    efectivamente inserta en una tabla (p.ej. fail2ban_logs) que todavía no
    existe por la pausa de 6.0. Si ese fallo aparece, debe atribuirse a 6.0
    (consecuencia esperada de la migración pendiente), no tratarse como un
    defecto nuevo.

    Este hallazgo también invalida, mientras persista, el criterio de cierre
    de FASE 11.3 ("no existen errores en logs tras reinicio").

    La corrección de código (incorporar la dependencia faltante,
    reconstruir la imagen monitoring-cron, redesplegar) queda fuera del
    alcance de esta revisión documental.

FASE 12 – POSIBLES MEJORAS FUTURAS (NO NORMATIVAS)
==========================================
Las siguientes propuestas no son obligatorias ni forman parte del modelo normativo actual.
Representan líneas de mejora futura.

Propuestas:
- Healthcheck específico del contenedor de cron.
- Job que verifique que otros jobs han corrido correctamente.
- Alerta de silencio (ausencia de eventos durante X horas).
- Unificación explícita del plano temporal del sistema.
- Checksum de configuración crítica para detectar desviaciones.
- Definición formal de un modo de aislamiento de contingencia que, en caso de fallo crítico de Docker, permita levantar sub-servicios mediante contenedores de recuperación minimalistas y efímeros, reforzando la prohibición absoluta de instalar dependencias de Python o ejecutar lógica de la aplicación directamente sobre el host de producción.
- Optimización de backups PostgreSQL
    Actualmente los backups se ejecutan mediante script Python que invoca pg_dump dentro del contenedor PostgreSQL.
    Una mejora futura podría simplificar el flujo utilizando directamente pg_dump desde el contenedor monitoring-cron.
    Arquitectura objetivo:
        monitoring-cron
        └ pg_dump -h postgres
    Ventajas:
        - Eliminación de capa Python intermedia
        - Simplificación operativa
        - Mayor compatibilidad con herramientas estándar
    Referencias:
        Ver ADR-0009-estrategia_backups_postgresql.md

Estas mejoras deberán formalizarse mediante ADR si se incorporan al modelo declarativo.
